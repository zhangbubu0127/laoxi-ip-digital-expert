# 老席留学IP数字专家 PRD

## AI 速读卡

- 一句话：一个飞书群，老板丢需求，一群 AI 专家（选题/写作/审核/学习/复盘）在主控调度下协作产出短视频内容，达到曝光、留资、信任三个目标。
- 形态：飞书群聊 = 唯一入口；单 bot（先用一个飞书自建应用）扮演全部专家，靠「【席X】」身份标签区分，后续可迁多 bot。
- 核心角色：主控调度 agent（路由/排期/熔断）+ 席小题（选题调研）+ 席小文（写手）+ 席小核（审核核实+外搜）+ 席小习（反馈学习）+ 复盘 agent（数据回流）。
- 关键机制：排期表（模板+数据+老板可覆盖）、自我迭代飞轮（diff学习）、熔断（token记账）、权限分级（老板 vs 发片同事）。
- 部署：本机 lark-cli 先跑通，解耦皮肤层/大脑层，为迁多 bot 铺路。

---

## 第一章：产品概述

### 1.1 背景与问题

老席是新加坡留学赛道 IP（13年行业老兵、北方口语、反常识劝退钩子）。当前内容生产的三个目标**全部未达成**：大曝光（流量起不来）、留资（有量没转化）、信任（咨询不成单）。现有生产靠人肉，慢且不稳定，且没有系统性的排期和复盘机制。

### 1.2 产品目标

通过「群聊多专家协作」形态，把内容生产从「人肉散打」升级为「系统作战」：
- **曝光**：选题调研驱动，踩热点、反常识钩子，提高被算法选中概率。
- **留资**：内容按目标分类（曝光/留资/信任）排期，留资内容带明确 CTA。
- **信任**：审核红线把关 + 人工发布确认 + 数据回流验证，建立可信循环。

### 1.3 可行性边界

- **本产品不解决发布**：智能体不能发片，发片是人工动作，发布后同事回群确认。
- **不解决投放执行**：投流/矩阵是真人运营的活，AI 只给决策支持（排期建议）。
- **不保证外部事实绝对正确**：AI 靠知识库 + 外搜，最终权威在知识库维护。
- **「AI 学习」是规则/记忆积累**，可解释、可撤销，非权重更新。

## 第二章：整体布局与导航

### 2.1 产品形态

飞书群聊。无独立 App、无网页端（本机阶段）。老板的全部操作都发生在群里，通过自然语言完成。

### 2.2 群聊消息视图（老板视角）

```
─────────────────────────────────────
 飞书群 · 老席留学数字专家
─────────────────────────────────────
 老板：帮我出3个没拍过的选题，信息差角度
 【席小题】基于本周调研，推荐3个：
          1. 预算不够？这条路线最省（留资向）
          2. 别去新加坡？那去哪（曝光向）
          3. 老席13年为什么不涨价（信任向）
 老板：第1个写条脚本，60秒
 【主控调度】流程：席小题选题已确认 → 席小文写作 → 席小核审核
 【席小文】脚本 v1 已出：…
 【席小核】审核通过，无红线，1条黄线建议改
 【主控调度】全流程完成。要发布版还是改？
─────────────────────────────────────
```

### 2.3 导航规则

| 老板意图 | 入口 | 系统响应 |
|---|---|---|
| 出选题 | 说「出选题」或 @席小题 | 派单席小题 |
| 写脚本 | 说「写脚本关于XX」 | 流水线 小题→小文→小核 |
| 看排期 | 说「看排期表」 | 贴当前排期表 |
| 改排期 | 说「下周三要3条曝光」 | 改排期表标记老板指定 |
| 圆桌讨论 | 说「大家讨论下XX」 | 多个专家身份并行发言 |
| 反馈修改 | 说「这个脚本不行」+ 贴改稿 | 席小习做 diff 学习 |
| 确认已发 | 发片同事说「8/3已发布」 | 排期表状态标已发 |

## 第三章：核心模块详细设计

### 模块 A：主控调度 agent

**职责**：群聊路由、排期管理、熔断、token 记账、知识检索。

**状态流转**：
```
收到消息 → 识别身份（老板/同事）→ 判断触发形态
  ├─ 定向（@席X / 说名字）→ 派单给该专家
  ├─ 意图（写脚本/出选题）→ 选流水线派单
  ├─ 排期指令 → 改排期表 → 回显
  └─ 默认（无触发）→ 回「需要我做什么？」
→ 汇总专家产出 → 发回群 → 记 token → 熔断检查
```

**失败路径**：
1. 意图识别不出 → 回「我没听懂，你要出选题/写脚本/看排期/讨论？」
2. 专家调用超时 → 重试1次，仍失败回群明说。
3. token 接近熔断阈值 → 提前报告，建议暂停/降配。

**硬约束**：主控是唯一调度者；专家被派单才说话（除圆桌）；排期表唯一写权限在主控。

### 模块 B：席小题（选题 + 调研合体）

**职责**：基于知识库 + 市场调研（热点/竞品/家长痛点），产出选题。调研是选题的组成部分，不单设调研角色。

**输出**：选题清单，每条标注类型（曝光/留资/信任）、调研依据、角度。

**状态流转**：接单 → 拉调研（热点+竞品+知识库）→ 出选题清单 → 回群。

**失败路径**：
1. 调研源不可用 → 用知识库兜底，标注「调研降级」。
2. 选题被老板否 → 记录否因，下次避开同方向。

**硬约束**：选题必须带类型标签（排期依赖）；选题角度须有调研或知识库依据，不空想。

### 模块 C：席小文（写手，内嵌风格）

**职责**：基于选题 + 知识库 + 风格档案产出多版文案。含原「席小风」的风格打磨职责（风格是写作约束，不是独立环节）。

**输出**：脚本 v1/v2…，附结构拆解、封面文字、钩子词、投放建议。

**状态流转**：接选题 → 匹配知识域 → 选钩子模板 → 按风格写作 → 自检 → 出稿。

**失败路径**：审核退回（红线）→ 按被拒原因重写，不把失败稿发群。

**硬约束**：费用数字必须与知识库一致，不能随口编；自称「老席」；无书面过渡词；合规红线零容忍。

### 模块 D：席小核（审核 + 核实 + 外部搜索）

**职责**：风格红线审核 + 库内事实核实 + **联网搜索核对外部事实**。含原「席小实」的核实职责。

**审核输出**：红线/黄线/通过判定，每条带理由；外部搜索信息标来源、标置信度。

**状态流转**：接脚本 → 库内核对 → 外搜核对 → 出判定 → 通过发主控 / 退回小文。

**失败路径**：
1. 知识库查不到 → 不硬编，发群 @老板 提问。
2. 外搜也拿不准 → 标「低置信度」发群问老板，绝不编造。

**硬约束**：任何不确定事实必须走「问老板」，禁止静默编造。

### 模块 E：席小习（反馈学习，自我迭代核心）

**职责**：对比 AI 原版 vs 老板修改稿，提炼可复用规则，确认后写入风格档案/memory。

**输出**：提炼的规则 + 给老板的确认询问 + 定期（每周）学习汇报。

**状态流转**：
```
老板贴修改稿 → diff AI原版vs老板版 → 分析每处改动原因
→ 提炼规则 → 群里问「我学到这条规则了对吗」
→ 老板确认 → 写入风格档案/memory → 跨会话生效
→ 定期汇报本周学到的规则，老板可删
```

**失败路径**：老板不同意提炼的规则 → 丢弃该规则，记录「被否规则」。

**硬约束**：每次学习当场求确认（A方案）；L1主观层老板说了算，L2客观层需数据验证才强化。

### 模块 F：复盘 agent（数据回流，飞轮闭环）

**职责**：收集发布后数据（笔记API + 人工兜底），沉淀验证结论，通知主控调排期。

**输出**：数据回流表更新、验证结论、排期调整建议。

**状态流转**：排期表有「已发」→ 等数据（API/人工）→ 分析 → 写 memory/验证结论 → 通知主控调后续排期。

**失败路径**：
1. 数据缺失 → 排期表标「待回流」，定期催老板补。
2. API 拿不到 → 人工兜底录入。

**硬约束**：学习层 memory 只有复盘 agent 写；数据缺失必须显式标注，不猜测。

### 模块 G：排期表

**形态**：本机用本地 Markdown 表，稳定后迁飞书多维表格。主控唯一写权限。

**结构**：`日期 | 内容类型 | 选题 | 目标 | 状态 | 负责人 | 数据回流`

**状态机**：`待产 → 审核中 → 待发 → 已发（人工确认）→ 回流完成`

**硬约束**：已发状态必须人工确认（智能体不能发片）；老板可覆盖任何排期。

## 第四章：超越竞品的差异化功能

**核心差异化不是功能，是「信任」机制的完整性**：

| 能力 | 竞品一般做法 | 本产品 |
|---|---|---|
| 审核 | 只查风格 | 风格红线 + 库内核实 + **外部搜索核对** + 不确定发群问老板 |
| 学习 | 靠人记 | **席小习 diff 学习**：改稿→提炼规则→当场确认→写入→数据验证 |
| 排期 | 无 | 排期表：模板+数据微调+老板覆盖，已发人工确认 |
| 反馈 | 无 | 熔断 + token 记账，不闷头烧钱 |
| 权限 | 无 | 老板 vs 发片同事分级，越权拦截 |
| 群形态 | 单窗口 | 多专家身份标签协作 + 圆桌模式 |

## 第六章：技术架构

### 6.1 分层（解耦，核心）

- **皮肤层**：飞书 bot（lark-cli）。收发消息、识别 sender、权限拦截。
- **大脑层**：专家逻辑（选题/写作/审核/学习/复盘），不依赖 bot 形态。
- **管道**：皮肤↔大脑之间约定接口，传消息内容 + 身份信息。
- **存储层**：knowledge/（事实层只读）、workspace/（工作层）、memory/（学习层）。

### 6.2 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 消息收发 | lark-cli（im.message.receive_v1 事件 / messages-send） | 已装已登录，验证过 |
| 事件消费 | lark-cli event consume | 常驻监听群消息 |
| 专家执行 | Claude Code 多角色 | 一个大脑多身份 |
| 知识存储 | 本地 Markdown 文件 | 先文件后多维表格 |
| 外搜核对 | Claude Code WebSearch | 席小核用 |
| 数据回流 | 笔记API（已做过）+ 人工兜底 | 搭完验证替代性 |

### 6.3 可替换与不可变

- **不可变（硬约束）**：皮肤/大脑解耦；已发人工确认；异常走问老板；知识库只读；排期表主控独写。
- **可替换**：bot 数量（单→多）、排期表存储（文件→多维表格）、数据源（API→人工）、专家数量。

## 第七章：交互细节

### 7.1 触发形态（同时存在）

1. 显式：@席X + 需求 → 定向派单。
2. 隐式：说「写脚本/出选题/审核」→ 主控识别意图。
3. 定向：说专家名字 → 只派该专家。
4. 默认：无触发 → 主控回「需要我做什么？出选题/写脚本/看排期/讨论？」

### 7.2 发言权

- 专家：被派单才说话（除圆桌）。
- 主控：随时在场兜底。
- 老板：最高权限，可打断、可改、可删。
- 发片同事：只可回「已发布」、回填数据，越权被皮肤层拦截。

### 7.3 圆桌模式

- 触发：难选题或老板喊「大家讨论下」。
- 表现：主控以多身份连续发标签消息（【席小题】【席小核】【席小文】）。
- 失控保护：刷屏/跑偏时主控中断，收敛为「各自给一版，主控汇总」。

### 7.4 排期表操作

- 看：老板说「看排期表」→ 贴表。
- 改：老板说「下周三要3条曝光」→ 主控改表标 bossOverride。
- 确认已发：发片同事说「8/3已发布」→ 状态待发→已发。

## 第十章：性能指标

| 指标 | 目标 | 测量方法 | 降级阈值 |
|---|---|---|---|
| 群消息响应 | ≤ 30s 出首个反馈 | 记录 receive→send 耗时 | >60s 需告警 |

| token 熔断 | 累计 1 亿 token 触发 | 主控记账 | 按费用调整 |
| 审核召回 | 红线零漏过 | 抽检已发内容 | 漏 1 条即告警 |
| 学习确认率 | ≥ 70% 规则被老板接受 | 席小习统计 | <50% 需调提炼质量 |
| 数据回流完整度 | ≥ 80% 已发内容有回流 | 排期表统计 | <60% 需催补 |

## 第十一章：开发者交接说明

### a) 先建什么
先建 P0 闭环：皮肤层（lark-cli 收/发消息）+ 大脑层主控调度 + 排期表文件 + 席小题/席小文/席小核 基础流水线。跑通「老板说写脚本 → 出稿 → 审核 → 回群」即第一个里程碑。

### b) 不要改什么（硬约束）
- 皮肤/大脑解耦，迁移多 bot 只换皮肤层。
- 已发状态必须人工确认，智能体不能自动标已发。
- 任何不确定事实走「问老板」，禁止静默编造。
- 知识库事实层只读；排期表主控唯一写权限；memory 学习层复盘 agent 独写。

### c) 可以自由发挥的地方
- 专家数量、角色命名、排期模板节奏、圆桌触发条件、数据回流源（API 或人工的替换方式）。

### d) 已知的未知项
- 笔记API 能否替代人工数据回流 —— 待系统搭完验证。
- 老板和发片同事的飞书 open_id —— 拉群后获取并绑定角色。
- 飞书自建应用凭证 —— 本机阶段创建 1 个；迁多 bot 再建更多。
- 排期模板的默认节奏数字 —— 需用真实数据校准。

### e) 验收剧本
1. 在飞书群说「帮我出3个选题」→ 收到席小题选题清单，各带类型标签。
2. 说「第1个写脚本60秒」→ 收到席小文脚本 v1 + 席小核审核结论。
3. 说「看排期表」→ 收到当前排期表。
4. 说「下周三要3条曝光」→ 排期表出现 3 条曝光标记 bossOverride。
5. 模拟发片同事身份说「8/3已发布」→ 该条状态变已发。
6. 贴一段改稿给席小习 → 席小习提问「我学到这条规则了对吗」，确认后写入。
7. 越权测试：发片同事身份说「改排期」→ 被拦截提示无权限。
