# 老席留学IP数字专家 · 需求与决策记录

> 本文档是项目决策的**唯一实时记录**。随对话推进持续追加，防止上下文压缩丢失信息。
> 最后更新：2026-08-02（2.18 圆桌/写脚本逐步输出）

## 一、项目定位

群聊里多个专家协助老板（老席）的内容生产，达到**大曝光、留资、获得信任**三个目标。
技术形态：通过飞书群接入，多智能体协作，小席agent统一编排。

## 二、已确认的核心决策

### 2.1 「从0」的边界
- **架构从0重建**：专家团、群聊协作、飞书接入整套架构重新设计，不沿用旧skill/旧agent。
- **业务资产保留当原料**：老席人设、家长原话库、爆款规律、合规红线、费用数据等市场验证过的内容继续使用。
- 老资料（laoxi skill、老席审核agent、knowledge结构）只做参考，不作为架构蓝本。

### 2.2 目标现状
- 曝光、留资、信任**三个都没有**，全部要建。不是选一个，是三个引擎并行。

### 2.3 小席agent（新增顶层角色）
- 负责**内容日历排期**：哪类内容（曝光/留资/信任）、什么时候发、发多少。
- 排期表发到飞书群，老板直观看到。
- 排期依据：**固定模板 + 数据反馈微调 + 老板一句话可覆盖**（三选一，用户选了此组合）。

### 2.4 数据回流
- 用户之前用**笔记API拉过平台数据**——保留，系统搭完先验证它能否替代人工。
- 与人工录入**结合**，人工兜底。

### 2.5 群聊形态
- **平时流水线派单**：老板发需求→小席→派单→专家产出→回群。
- **偶发圆桌**：难选题或老板喊「大家讨论下」时，多个专家临时讨论，平时不废话。

### 2.6 熔断机制
- 记录每次调用token消耗，累计到阈值触发熔断，主动报告，不闷头烧钱。
- 阈值先设 **1亿token**，用户按费用再调。

### 2.7 审核强化
- 席小核不只对照知识库，**调用联网搜索核对外部事实**（费用/政策/院校）。搜到的信息标来源、标置信度。
- **不确定点主动发群**：知识库没有、搜索也拿不准的点，不硬编，在群里 @老板 确认，等答复再继续。

### 2.8 部署路径
- **先本机跑通完整流程**（成本0，验证架构）。
- 验证有价值后再决定是否转独立服务（需云服务器+飞书自建应用凭证）。
- 通过**飞书自建应用**接入群聊，之后拉群聊。

## 三、智能体评估结论（含合并）

| 方案角色 | 判定 | 理由 |
|---|---|---|
| 席小风（风格打磨师） | 合并→席小文 | 风格是写手的约束参数，不是独立工作流 |
| 席小题（选题策划师） | 保留 | **选题+调研合体**，不单设席小材 |
| 席小实（内容核实专家） | 合并→席小核 | 核实是审核的前置步骤 |
| 席小文（内容写手） | 保留 | 核心产出者，内嵌风格 |
| 席小核（内容审核） | 保留 | 审核=风格红线+事实核实+外部搜索核对 |
| 复盘agent（新增） | 保留 | 数据回流→排期调整→知识库更新，方案原缺 |
| 管家/小席 | 保留并升级 | 路由+排期+熔断+知识检索 |

**核实边界（重要）**：
- 库内核对：对照知识库查一致/出处 → AI能自动做
- 外部独立验证：从零验证外部事实 → AI不能独立保证，靠搜索+数据源权威性，责任在知识库维护

### 2.9 自我迭代 / 数据飞轮
- **新增角色：席小习（反馈学习agent）**，加入智能体组。
- 机制：老板在群里贴修改稿 → 席小习对比 AI原版 vs 老板版（diff）→ 分析改动原因 → 提炼成可复用规则 → **当场在群里向老板确认「我学到这条规则了对吗」** → 确认后写入风格档案/memory → 跨会话生效。
- 分级学习：
  - L1 主观层：老板当场确认的偏好 → 直接写入风格档案，老板说了算。
  - L2 客观层：数据回流验证的偏好 → 只有数据证明有效才强化。
- **A + 定期汇报**：每次改动当场求确认（透明）+ 定期（拟每周）发群汇总「本周学到的规则」，老板可删。
- 学习本质 = 规则库/记忆的积累（可解释、可撤销），非权重更新，不会顿悟只会积累。
- 不需要额外harness框架：Claude Code原生够用，缺的是「反馈学习」这个专门环节，不是框架。

## 五、角色触发规则（已确认）

**小席agent —— 群聊「路由」，兜底接一切**

| 老板在群里说 | 主控做什么 |
|---|---|
| 「帮我出个选题」 | 派单给席小题 |
| 「写条脚本，关于XX」 | 走流水线：席小题→席小文→席小核 |
| 「看下排期表」 | 贴出当前排期表 |
| 「下周三前要3条曝光内容」 | 改排期表，标记任务 |
| 「大家讨论下XX」 | 触发圆桌模式，多个专家发言 |
| 「这个脚本不行」 | 转给席小习做diff学习 |

**触发词三种形态 —— 同时存在，不互斥**：
1. 显式命令：老板 @agent名 + 需求 → 直接派单
2. 隐式意图：老板说"写脚本/出选题/审核"（不@）→ 主控识别意图派单
3. 默认状态：老板说了句没触发关键词的话 → 主控不瞎动，回「需要我做什么？出选题/写脚本/看排期/讨论？」
- 三者并存：@点名、说人话都能被识别，老板不用记agent名字，怎么顺口怎么说。

**发言权边界**：
- 席小题/席小文/席小核/席小习/复盘agent：**被派单才说话**，平时不抢话（除圆桌模式）
- 小席：**随时在场**，兜底接话
- 老板：最高权限，可打断、可改、可删

### 2.11 飞书接入方式（已确认）
- 用 **lark-cli**（已装、已登录，飞书官方CLI）。
- **只建一个飞书自建应用 = 一个 bot**。六个专家不建多个bot，靠消息内身份标签区分（如「【席小题】...」）。理由：成本低、不刷屏、权限好管。
- lark-cli 已验证能力：`im.message.receive_v1` 事件（接收群消息）、`+messages-send`（发消息）、`+chat-messages-list`（拉历史）、`event consume`（事件消费）、`config bind --app-id`（技术上可多账号，但本项目不需要）。

### 2.12 权限模型（已确认）
- 通过 `im.message.receive_v1` 的 `sender` 识别消息发送者，映射到角色。

| 身份 | 权限 |
|---|---|
| **老板**（拉群后用户指定谁是老板） | 最高：派单、改排期、确认规则、删规则、开圆桌 |
| **产品**（运营者，如张布布） | 与老板同级最高权限，身份标签区分 |
| **发片同事** | 只允许：回「已发布」、回填数据（播放/留资），不能派单/改排期 |

### 2.13 bot架构决策（已确认）
- **先单bot再迁多bot，两阶段**。先本机单bot验证逻辑，确认有价值后迁多bot加团队感。
- **解耦原则（架构核心）**：把「消息收发层」（皮肤）与「专家逻辑层」（大脑）彻底分离，中间用约定管道传话。
  - 皮肤层：只管收发消息（接收群消息、发消息、@/权限识别）。
  - 大脑层：专家逻辑（选题/写作/审核/学习/复盘），完全不依赖是哪个bot。
  - 迁移时只换皮肤：1个event监听→6个、文本标签→独立账号、1个app→6个app。知识库/排期表/专家逻辑/权限/熔断全部复用。
- 形象比喻：换前台服务员（bot），后厨菜谱（专家逻辑）不用改。

## 六、排期表形态（已确认）

排期表 = 小席agent唯一写权限。本机阶段用本地Markdown表验证，稳定后可迁飞书多维表格。

```
| 日期 | 内容类型 | 选题 | 目标 | 状态 | 负责人 | 数据回流 |
|------|---------|------|------|------|--------|---------|
| 8/3  | 曝光    | 普娃逆袭  | 拉新 | 待产 | 席小文 | — |
| 8/4  | 信任    | 老席自述  | 建信任 | 审核中 | 席小核 | — |
| 8/5  | 留资    | 预算对比  | 转化 | 已发 | 席小文 | 播放2.1w 留资23 |
| 8/6  | 曝光    | 政策解读  | 拉新 | 已排 | 席小文 | — |
```

**核心规则：**
1. **三类内容按模板排期** —— 默认节奏（如每周3曝光+2信任+2留资），排期表按此生成，老板可改。
2. **数据驱动微调** —— 复盘agent把发布后数据写回「数据回流」列，小席根据表现调整后续排期。
3. **老板可覆盖** —— 老板说「下周三要3条曝光」，主控直接改表，标记老板指定。
4. **状态流转 —— 已发必须人工确认**：
   - 智能体**不能发片、不能自动标「已发」**。
   - 流程：待产→审核中→待发 → **人工发片后，发片同事在群里回「8/3这条已发布」→ 智能体才标「已发」** → 进入数据回流等待。

### 2.14 LLM 后端（已确认，2026-08-02）
- 专家出内容**必须用大模型，基本盘**。P0 初期规则版仅作管道占位，现已替换为真实 LLM。
- 后端：**MiMo API 主力**（模型 **mimo-v2.5-pro**）+ **DeepSeek 备用**（`config/secrets.json` 里可改）。
- API key 走 gitignored 的 `config/secrets.json`，不进代码/commit/日志。
- 架构：`src/brain/llm.py`（MiMo 主力 + DeepSeek 备用客户端，stdlib urllib，零依赖）+ `src/brain/knowledge.py`（知识库加载）+ 各专家 `读知识库→拼 prompt→调大模型→回群`。
- 每位专家的 prompt 内含角色设定与硬约束（席小文：自称老席/费用数字以知识库为准/无书面过渡词/合规红线零容忍；席小核：红线审核+库内核实+不确定标「需老板确认」）。
- 席小核红线词先本地规则拦截（确定性），再交 LLM 全量审核。
- 熔断记账仍按 token 累计（2026-08-02 补齐持久化：init 读盘恢复，重启不丢）。
- 外搜核对（2026-08-02 已实现 v1）：无搜索 API key、不装新依赖 → `src/brain/search.py` 用 stdlib urllib 调 Wikipedia API（免 key），院校/排名/国家事实可核；核不到 → 标「需老板确认 · 低置信度」；模块化，将来给搜索 API key 可换。
- 席小习学习（2026-08-02 已实现 v1）：老板贴修改稿 → diff AI原版 vs 老板版 → 提炼 ≤3 条规则 → 待确认 → 回「确认」写入 `memory/学习规则.md` → 已确认规则注入席小文生产 prompt。
- 复盘数据回流（2026-08-02 已实现 v1）：报数据（如「8/5 主题 播放2.1w 留资23」）→ 排期表 data 落盘 + 状态=回流完成 → 追加 `memory/数据回流.md` → 复盘 agent 出验证结论 + 排期调整建议 → 追加 `memory/验证结论.md`。

### 2.15 意图识别 + 会话上下文连续性（已确认，2026-08-02）
- **意图识别升级为 LLM 判定**：替换纯关键词路由，主控路由用 LLM 把用户消息归类到闭合意图集（出选题/写脚本/看排期表/改排期/确认已发布/反馈修改/追问/其他），并抽取 count/topic/date/content_type 参数。关键词 `by_keyword` 仅作 LLM 失败时的降级兜底。
- **会话记忆（硬要求）**：`src/brain/session.py` 按 `chat_id` 保存最近 **7 轮**对话（LRU），每轮 = 一条用户消息 + 全部 agent 回复；意图识别把 7 轮历史拼进 prompt，专家派单带最近 2 轮上下文。
- **三个连续性场景闭环**：① 出选题后「第1个写条脚本」→ 席小文按第 1 个选题写；② 出内容后「这个脚本不行」→ 反馈修改，路由给最近一条产出者改写；③ 针对返回答案「为什么选这个角度」→ 追问，路由给产出者讲依据（讲清依据、不编造）。
- **权限**：反馈修改/追问并入 admin-only（老板/产品），发片同事不可用；无上一条产出时回「没有找到可修改/可追问的上一条产出」，不静默。
- **文档规范（硬要求）**：改动涉及旧文档时，先拷贝旧版到 `docs/archive/`（命名 `原名-YYYYMMDD-HHMM.md`），再改；每次迭代记录写 `docs/iteration/`，两者分开不混。

### 2.16 泛类内容素材化 + 完整讨论记录（已确认，2026-08-02）
- **素材库**：用户投喂的泛类内容（热点文章/竞品爆款/灵感）存 `workspace/素材/`（工作层，不破坏 knowledge/ 事实层只读）。老板说「记素材：<内容>」→ 主控存成带时间戳的素材文件；席小题出选题时把最近 5 个素材并入 prompt，结合知识库出题。
- **原文直传**：出选题时把用户本条消息原文作为 context 传给席小题（此前只传参数、原文被丢弃），同一条消息里贴内容+出选题可被使用。
- **完整讨论记录**：皮肤层经 lark-cli `+chat-messages-list --as bot` 拉最近群历史（只留真人文本发言、跳过 bot 自 reply），注入大脑层接缝 `_pull_history`（解耦约束：大脑层不直接调 lark-cli）。出选题并入席小题上下文；「看完整讨论」意图拉取并展示。
- **权限**：记素材/看完整讨论并入 admin-only（老板/产品）。
- **素材冲突**：素材与知识库冲突时以知识库事实为准（席小题铁律）；素材库 v1 只做追加。

### 2.17 圆桌模式落地 + 身份标签修复（已确认，2026-08-02）
- **背景**：老板说「开圆桌会议」无反应。查证：圆桌本属 P2 未实现（意图集无「圆桌」、主控无圆桌分支）；且该消息撞上意图识别 LLM 截断 bug（reasoning 模型把 400 输出 token 全烧在"思考"上，长历史时截断无 JSON → 降级关键词 → 被"选题"二字误判成出选题）。单 bot 设定本身不是障碍——架构 §8 本就设计单 bot 多视角并行。
- **圆桌 v1（已落地）**：新增「圆桌讨论」意图（LLM taxonomy + by_keyword 兜底「圆桌/讨论下/讨论一下/大家+讨论」）；主控 `_roundtable` 抽议题（LLM topic 参数 → 「第X条」定位上一条专家产出对应条目（支持中文数字「第二条」）→ 上一条产出首行 → 原文清洗），派给席小题（选题）/席小文（内容）/席小核（审核）三视角各一版 ≤180 字，主控汇总成**单条【圆桌纪要】**发群；无议题回引导不空转；单专家失败标「未给出意见」不拖垮全场。
- **意图识别截断修复**：`recognize()` max_tokens 400→800，降低 reasoning 模型长历史截断率。
- **身份标签修复（重要）**：`lark_bridge.run_loop` 发回复此前未用 `format_outbound`，所有回复裸文本无【席X】前缀——单 bot 靠文本标签区分身份的机制实际没生效。改用 `format_outbound(reply)` 后回复带身份前缀，恢复团队感。
- **权限**：圆桌讨论并入 admin-only（老板/产品）。

### 2.23 审核体验四联修：连续性 + 脚本不刷屏 + 结论精简问理由 + 三态判定（已确认，2026-08-04）
老板一次提 4 个问题，全部查根因后修掉：
- **问题1 写脚本连续性（选题指代）**：根因——主控把「第N个写条脚本」直接当任务传给席小文，席小文无选题列表约束，凭感觉自由发挥。修复：`_resolve_script_task()` 把「第N个」解析成上一条席小题产出的具体选题文字，`xiaowen.handle` 加硬性要求「任务给了选题/选题列表必须严格写指定的那条，禁止发明替换泛化」。
- **问题2 审核不刷屏（脚本进后台）**：根因——脚本被拼进 @派单 task，全文发群。修复：派单任务只写「审核这条脚本」，脚本原文走 `context_store` 上下文（`_context_put`→专家 `take`），群里不再复述；`xiaone.handle` 红线扫描连 task+context 一起扫。

- **问题4 审核误判 bug**：根因——主控 `_verdict_needs_change` 子串匹配「红线」，真实输出「通过：无红线」含「红线」被误判为需改 → 误发重写指令给席小文。修复：改**三态判定** `_verdict_classify`（通过/不通过/需老板确认），只认明确拒稿信号（不通过/未通过/❌/需改）与疑问信号（需老板确认/待确认），绝不扫「红线」词面。

- 行为契约：确认语永不生成占位垃圾；类型永远来自刚定稿脚本或选题清单行首标签，不硬编码。

### 2.26 「说到做到」：查选题记录真核对 + 存档持久化（已确认，2026-08-05）
老板需求：老板问「刚才的选题你还能看到么」，小席说「我去核对原始记录」就必须真核对；说「让席小题重新整理」就必须真派单，不能只生成聊天话术就停。
- **根因**：①`context_store.sweep(600)` 把 basis/review **存档**当临时上下文 10 分钟清掉（`take()` 特意排除存档、`sweep()` 没有），记录不持久；②会话记忆是进程内存，重启即空；③「查选题记录」类请求意图归「其他」，只走闲聊生成，无任何真实动作。
- **存档持久化契约**：`workspace/上下文/` 里 `_basis.json`（席小题选题清单+依据）/`_review.json`（席小核审核详情）是**固定存档**，sweep 永不删除、被新产出覆盖（有界）；临时派单上下文仍 10 分钟清理。
- **真核对契约**：老板问「刚才的选题还能看到么」类请求 → 小席真读存档/会话记忆回执真实选题清单（含类型标签）；无存档但有方向可恢复 → **真实派单席小题重出一版**；都无 → 如实说没找到（不编造）+ 引导老板给方向。
- **闲聊不承诺契约**：闲聊话术禁止承诺「我这就去核对/查/派单」等未执行系统动作（说了等于谎报）；需要查记录/排期引导老板说明确指令，系统真查真做。

### 2.27 「提议→肯定→真执行」闭环：小席提议带标记，老板点头后真实执行（已确认，2026-08-05）
老板需求：小席聊天里提议的下一步（重出选题/写脚本/审核）是好的想法，希望老板给了肯定答复后，小席真的去执行，而不是只停在话术。
- **机制**：小席闲聊 prompt 规定——主动提议下一步时，句末必须加固定标记【提议】<动作>：<内容>；`_chat_reply` 把标记登记为 `_pending_action[chat_id]`（intent/params/task/ts），对外展示剥离标记；老板回短肯定词（好/要/可以/行/嗯…8字内）且无未决规则 → `_route_intent` 按标记意图真派单真执行。
- **动作白名单**：出选题/重新整理选题/写脚本/审核脚本/看排期表。改排期不在白名单（需具体日期选题，聊天锁定不了，肯定回复会丢细节 → 落占位垃圾，与 2.25 同类）；2.26「闲聊不承诺契约」升级为「提议必须带标记，带标记=承诺、无标记=纯话术」。
- **过期**：待定动作 3600 秒未确认自动作废（进程内），防陈旧确认误触发。
- **优先级**：wait_boss 挂起（审核疑问 @老板）先于提议确认；无待定动作时肯定词走正常意图路由不劫持。

### 2.28 「理解人话 + 说话即行动」：承诺即兑现契约（已确认，2026-08-05，提示词优化专家流程）
老板需求：智能体「不够智能」——老板问「刚才的选题你还能看见么」，小席回得暖心但没真核对、没派单，只是空话。用提示词优化专家技能做，老板拍板「架构级放开」。**契约升级线：2.26「闲聊不承诺」→ 2.27「提议必须带标记」→ 本迭代「承诺即兑现」**——不再压制自然回复，而是把承诺建模成代码可解析的契约，让承诺在代码层有出口，不靠模型自觉。
- **根因三层**：①「能看见」不在 2.26 关键词表（只认「看到/还能看到/还在/记录/丢/回顾/哪去了」）→ 例子被归闲聊；②闲聊分支执行依赖 2.27 死板【提议】标记，LLM 把提议说成自然口语（「要不要让席小题…」）就不带标记 → 登记不了 → 空话；③意图层无「查记录」意图，这类 meta 查询全塌进「其他」。
- **意图层**：INTENTS 增「查记录」；`by_keyword` 加 `_LOOKUP_HINTS` 兜底（能看见/还在/在哪/丢了/回顾…，判定放「选题→出选题」之前）；用例防误伤「把刚才那个选题写条脚本」仍走写脚本。
- **执行契约【行动】JSON**：小席聊天回复末尾可带 `【行动】{"action":..,"task":..,"when":"立即|待确认"}`——立即动作（核对选题记录/看排期表）`_run_immediate` 当场真执行并补回执；待确认动作（重新出选题/写脚本/审核脚本）登记 `_pending_action`，老板回「好/要/可以」真派单；`_chat_reply` 展示剥离行动行。2.27 的【提议】标记保留作兼容层。
- **专家提议**：专家被直接 @ 闲聊自回时，建议的可执行下一步带【动作名】标记（「要不要我【重新出选题】按预算方向出 3 个？」）→ `_register_expert_proposal` 识别登记；覆盖单进程直接 @ 路径（`_route_intent`）与多 bot 自回路径（`handle_bot_output`）。
- **专家理解人话**：五个专家（小题/小文/小核/小习/小盘）各补「理解老板的话」few-shot（老板口语→垂类任务的正确理解），不删任何已认可规则；席小核/席小习/席小盘严格不动解析依赖的输出格式（审核结论三段/规则 JSON）。
- **验证**：test_intent 29→32、test_controller 92→102，全量回归绿（controller 102 / intent 32 / experts 28 / context_store 10 / scheduler 8 / session 6 / market 7 / rules 6 / search 4 / pipe）；端到端老板飞书实测通过（16:20）——查记录真回执、重出选题真派单，均真执行；6 bot 已重启加载新提示词。
