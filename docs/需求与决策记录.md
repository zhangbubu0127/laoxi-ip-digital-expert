# 老席留学IP数字专家 · 需求与决策记录

> 本文档是项目决策的**唯一实时记录**。随对话推进持续追加，防止上下文压缩丢失信息。
> 最后更新：2026-08-01

## 一、项目定位

群聊里多个专家协助老板（老席）的内容生产，达到**大曝光、留资、获得信任**三个目标。
技术形态：通过飞书群接入，多智能体协作，主控调度agent统一编排。

---

## 二、已确认的核心决策

### 2.1 「从0」的边界
- **架构从0重建**：专家团、群聊协作、飞书接入整套架构重新设计，不沿用旧skill/旧agent。
- **业务资产保留当原料**：老席人设、家长原话库、爆款规律、合规红线、费用数据等市场验证过的内容继续使用。
- 老资料（laoxi skill、老席审核agent、knowledge结构）只做参考，不作为架构蓝本。

### 2.2 目标现状
- 曝光、留资、信任**三个都没有**，全部要建。不是选一个，是三个引擎并行。

### 2.3 主控调度agent（新增顶层角色）
- 负责**内容日历排期**：哪类内容（曝光/留资/信任）、什么时候发、发多少。
- 排期表发到飞书群，老板直观看到。
- 排期依据：**固定模板 + 数据反馈微调 + 老板一句话可覆盖**（三选一，用户选了此组合）。

### 2.4 数据回流
- 用户之前用**笔记API拉过平台数据**——保留，系统搭完先验证它能否替代人工。
- 与人工录入**结合**，人工兜底。

### 2.5 群聊形态
- **平时流水线派单**：老板发需求→主控调度→派单→专家产出→回群。
- **偶发圆桌**：难选题或老板喊「大家讨论下」时，多个专家临时讨论，平时不废话。

### 2.6 熔断机制
- 记录每次调用token消耗，累计到阈值触发熔断，主动报告，不闷头烧钱。
- 阈值先设 **1亿token**，用户按费用再调。

### 2.7 审核强化
- 席小核不只对照知识库，**调用联网搜索核对外部事实**（费用/政策/院校）。搜到的信息标来源、标置信度。
- **不确定点主动发群**：知识库没有、搜索也拿不准的点，不硬编，在群里 @老板 确认，等答复再继续。

### 2.8 部署路径
- **先本机跑通完整流程**（成本0，验证架构）。
- 验证有价值后再决定是否转独立服务（需云服务器+飞书自建应用凭证）。
- 通过**飞书自建应用**接入群聊，之后拉群聊。

## 三、智能体评估结论（含合并）

| 方案角色 | 判定 | 理由 |
|---|---|---|
| 席小风（风格打磨师） | 合并→席小文 | 风格是写手的约束参数，不是独立工作流 |
| 席小题（选题策划师） | 保留 | **选题+调研合体**，不单设席小材 |
| 席小实（内容核实专家） | 合并→席小核 | 核实是审核的前置步骤 |
| 席小文（内容写手） | 保留 | 核心产出者，内嵌风格 |
| 席小核（内容审核） | 保留 | 审核=风格红线+事实核实+外部搜索核对 |
| 复盘agent（新增） | 保留 | 数据回流→排期调整→知识库更新，方案原缺 |
| 管家/主控调度 | 保留并升级 | 路由+排期+熔断+知识检索 |

**核实边界（重要）**：
- 库内核对：对照知识库查一致/出处 → AI能自动做
- 外部独立验证：从零验证外部事实 → AI不能独立保证，靠搜索+数据源权威性，责任在知识库维护

### 2.9 自我迭代 / 数据飞轮
- **新增角色：席小习（反馈学习agent）**，加入智能体组。
- 机制：老板在群里贴修改稿 → 席小习对比 AI原版 vs 老板版（diff）→ 分析改动原因 → 提炼成可复用规则 → **当场在群里向老板确认「我学到这条规则了对吗」** → 确认后写入风格档案/memory → 跨会话生效。
- 分级学习：
  - L1 主观层：老板当场确认的偏好 → 直接写入风格档案，老板说了算。
  - L2 客观层：数据回流验证的偏好 → 只有数据证明有效才强化。
- **A + 定期汇报**：每次改动当场求确认（透明）+ 定期（拟每周）发群汇总「本周学到的规则」，老板可删。
- 学习本质 = 规则库/记忆的积累（可解释、可撤销），非权重更新，不会顿悟只会积累。
- 不需要额外harness框架：Claude Code原生够用，缺的是「反馈学习」这个专门环节，不是框架。

## 五、角色触发规则（已确认）

**主控调度agent —— 群聊「路由」，兜底接一切**

| 老板在群里说 | 主控做什么 |
|---|---|
| 「帮我出个选题」 | 派单给席小题 |
| 「写条脚本，关于XX」 | 走流水线：席小题→席小文→席小核 |
| 「看下排期表」 | 贴出当前排期表 |
| 「下周三前要3条曝光内容」 | 改排期表，标记任务 |
| 「大家讨论下XX」 | 触发圆桌模式，多个专家发言 |
| 「这个脚本不行」 | 转给席小习做diff学习 |

**触发词三种形态 —— 同时存在，不互斥**：
1. 显式命令：老板 @agent名 + 需求 → 直接派单
2. 隐式意图：老板说"写脚本/出选题/审核"（不@）→ 主控识别意图派单
3. 默认状态：老板说了句没触发关键词的话 → 主控不瞎动，回「需要我做什么？出选题/写脚本/看排期/讨论？」
- 三者并存：@点名、说人话都能被识别，老板不用记agent名字，怎么顺口怎么说。

**发言权边界**：
- 席小题/席小文/席小核/席小习/复盘agent：**被派单才说话**，平时不抢话（除圆桌模式）
- 主控调度：**随时在场**，兜底接话
- 老板：最高权限，可打断、可改、可删

### 2.11 飞书接入方式（已确认）
- 用 **lark-cli**（已装、已登录，飞书官方CLI）。
- **只建一个飞书自建应用 = 一个 bot**。六个专家不建多个bot，靠消息内身份标签区分（如「【席小题】...」）。理由：成本低、不刷屏、权限好管。
- lark-cli 已验证能力：`im.message.receive_v1` 事件（接收群消息）、`+messages-send`（发消息）、`+chat-messages-list`（拉历史）、`event consume`（事件消费）、`config bind --app-id`（技术上可多账号，但本项目不需要）。

### 2.12 权限模型（已确认）
- 通过 `im.message.receive_v1` 的 `sender` 识别消息发送者，映射到角色。

| 身份 | 权限 |
|---|---|
| **老板**（拉群后用户指定谁是老板） | 最高：派单、改排期、确认规则、删规则、开圆桌 |
| **发片同事** | 只允许：回「已发布」、回填数据（播放/留资），不能派单/改排期 |

---

### 2.13 bot架构决策（已确认）
- **先单bot再迁多bot，两阶段**。先本机单bot验证逻辑，确认有价值后迁多bot加团队感。
- **解耦原则（架构核心）**：把「消息收发层」（皮肤）与「专家逻辑层」（大脑）彻底分离，中间用约定管道传话。
  - 皮肤层：只管收发消息（接收群消息、发消息、@/权限识别）。
  - 大脑层：专家逻辑（选题/写作/审核/学习/复盘），完全不依赖是哪个bot。
  - 迁移时只换皮肤：1个event监听→6个、文本标签→独立账号、1个app→6个app。知识库/排期表/专家逻辑/权限/熔断全部复用。
- 形象比喻：换前台服务员（bot），后厨菜谱（专家逻辑）不用改。

## 六、排期表形态（已确认）

排期表 = 主控调度agent唯一写权限。本机阶段用本地Markdown表验证，稳定后可迁飞书多维表格。

```
| 日期 | 内容类型 | 选题 | 目标 | 状态 | 负责人 | 数据回流 |
|------|---------|------|------|------|--------|---------|
| 8/3  | 曝光    | 普娃逆袭  | 拉新 | 待产 | 席小文 | — |
| 8/4  | 信任    | 老席自述  | 建信任 | 审核中 | 席小核 | — |
| 8/5  | 留资    | 预算对比  | 转化 | 已发 | 席小文 | 播放2.1w 留资23 |
| 8/6  | 曝光    | 政策解读  | 拉新 | 已排 | 席小文 | — |
```

**核心规则：**
1. **三类内容按模板排期** —— 默认节奏（如每周3曝光+2信任+2留资），排期表按此生成，老板可改。
2. **数据驱动微调** —— 复盘agent把发布后数据写回「数据回流」列，主控调度根据表现调整后续排期。
3. **老板可覆盖** —— 老板说「下周三要3条曝光」，主控直接改表，标记老板指定。
4. **状态流转 —— 已发必须人工确认**：
   - 智能体**不能发片、不能自动标「已发」**。
   - 流程：待产→审核中→待发 → **人工发片后，发片同事在群里回「8/3这条已发布」→ 智能体才标「已发」** → 进入数据回流等待。
