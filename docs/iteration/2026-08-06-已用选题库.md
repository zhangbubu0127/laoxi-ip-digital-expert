# 迭代记录 · 2026-08-06 · 已用选题库

## 目标

老板担心多次使用时选题反复出现。建「已用选题库」单独存储已采用选题，出题时降权（优先新题，非硬排除），每次给完选题后提醒可查看，查看时按 10 条一页真分页。

**老板已拍板的关键决策**：
- **已采用判定**：排上排期表就算采用（`add_entry` 的真实选题即入已用库；占位多条不入）。
- **降权方式**：不是硬排除——出题时已用选题降权，优先新角度，实在没有新角度才可复用且不得原样照搬。
- **取材配额按数量自适应**（新反馈）：之前的选题混淆/重复，根因可能是取材配额硬约束「知识库/竞对/热点各占」——当要的选题 < 3 个时没法三类各占，席小题把单个选题硬凑多来源（10:28 依据拆条的深层根因）。`n < 3` 时不强制均衡，随机选一类或两类来源即可。

## 架构影响

- 新增 `workspace/已用选题.md` 独立于排期表（老板要求单独存）。
- 排期入已用只在真实选题处（`_route_intent` 的 `add_entry(picked)` 与 `_resolve_schedule` 的 `add_entry(entry)`），占位多条「曝光选题N」（`_schedule_entries`）不入。
- 出选题异步流程新增 wait_topic 等待态：与 wait_schedule 同级，超时安静撤（产出迟到的极端情况下提醒会丢，但产出席小题仍自发群，不影响展示）。
- 降权靠 prompt 软约束，LLM 极端情况下仍可能原样复用（尤其已用清单 >30 条只取最近 30）；后续仍重复再考虑硬排除或相似度过滤。

- 单测全量回归绿：used_topics（5）→ controller（145）→ intent（37）→ scheduler → context_store → session → experts（31）→ multi_main → identity。

  - 「看已用选题」→ 发 ≤10 条 + 问继续；回「继续」续发；回「够了」结束；全发完 → 「已全部展示已选用选题」。
  - 用户（已登记）也可查已用选题。

## 遗留/已知项

- 降权软约束 + 最近 30 条截断：极端情况可能复用旧题；已用库 >30 条后按需考虑硬排除/相似度过滤。
- wait_topic 超时安静撤：产出迟到的极端情况下提醒会丢（不影响席小题自发群展示）。
- 已用选题库独立于排期表；初始化时从现有排期灌一次，之后靠排期自动登记。
