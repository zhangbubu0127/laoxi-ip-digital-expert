# 迭代记录：标已发无日期标题回落最近定稿选题 + 日志跨日压缩幂等

日期：2026-08-10
关联：**8/10 测试群事故**——老板 16:40:45 发「@小席 已核对好，可以确定是已发了」（刚定稿、16:33 刚上排期表）→ 小席回「已发状态：没找到匹配的待发条目，说清日期+标题」。老板质疑：刚讨论的选题、刚上传多维表格，系统应该知道是哪条。前序：2026-08-09《排期意图修复与意图识别防误判》（v1.8）。

## 目标

确认已发布时，消息只回「已核对好，可以确定是已发了」这类**无日期无标题**的确认语，能靠会话上下文（刚定稿选题）定位到刚排期那条，标已发；定位不到/撞题时给可操作的追问，而不是干巴巴「没找到匹配的待发条目」。

## 根因

- 排期表里明明有那条行：8/10「"孩子国内上课都坐不住，去新加坡英文授课能毕业吗？"真实毕业率老席讲给你听」状态=待产（16:33:52「上排期表吧，排8/10 17:38」新增，16:34 同步飞书 6 行，16:38 还发过发布提醒）。
- `_try_mark_published` 只在消息显式带「日期+标题」、或标题能模糊命中时才定位行；消息无日期无标题 → 纯标题模糊匹配对不上 → 落「没找到匹配的待发条目」。
- 执行器**没有回落「最近定稿选题」（`_last_passed[chat_id]`）**——16:33「可以了」定稿时 `_record_passed` 已把刚讨论的选题二写入 `_last_passed`。这正是 8/8 排期意图兜底用的锚点，标已发这侧漏了。
- LLM 其实判对了 action=确认已发布（防呆「已发」也过了），缺的是**执行器用上下文定位行**，不是意图识别问题。

## 改动清单

**controller.py**
- `_try_mark_published(content, params, chat_id)` 新增 `chat_id` 参数。
- 无日期+标题也模糊不到时，回落 `_last_passed[chat_id]`：归一化最近定稿选题 → 对 待产/待发 行模糊匹配 → **唯一命中才标已发**（回「确认」）；撞题歧义（多条可对上）不猜，明说「说下日期或标题，我好确认是标哪条已发」；无匹配维持原「没找到匹配的待发条目，说清日期+标题」。
- `_exec_mark_published` 传入 `msg.chat_id`。

**log.py（顺带修的日志丢失 bug）**
- 8/10 起小席进程跨日滚动时 `_compress_file` 抛 `FileNotFoundError: system-2026-08-09.log`（该文件已被另一 bot 进程启动时 `_cleanup()` 压缩成 .gz），导致每一条路由/LLM 日志 `emit` 失败被丢弃（本次事故 16:40 的路由/规划器日志就是因此缺失，只能靠 lark_bridge 日志重建现场）。
- `_compress_file` 幂等：文件不在直接跳过；`_ensure_stream` 跨日压缩失败 try/except 吞掉，不阻塞切新文件，记录照样落盘。

## 架构影响

- 标已发行定位从「只认消息里的日期+标题」扩为「日期/标题显式 → 标题模糊 → **`_last_passed` 上下文回落**」三层，与 8/8 排期意图兜底同源（`_last_passed` 是「刚定稿选题」的模块态锚点）。
- 高后果动作（标已发）仍守「不猜」底线：唯一命中才标，撞题歧义必须追问，防误标。
- 局限：`_last_passed` 是模块态，进程重启后清空。重启后无日期+标题的确认语仍需老板带上标题/日期，或重跑一条流水线重建上下文；连续运行（真实生产流程定稿→排期→确认在一个会话内）不受影响。
