# 迭代记录：确认已发布 / 数据回流自然语言化（排期表不再要求「日期 选题」标准格式）

日期：2026-08-08
关联：**老板反馈**（飞书 09:24-09:26）——「昨天发布的视频今日浏览3450、点赞87、评论3、收藏2、转发3，为我录入；并且复盘」→ 小席回「当前没有待回流数据」；「《新加坡私校集体收紧，初中直通本科这条路要断了吗？》已发布，更新，并且记录刚刚的数据」→ 小席回「格式不对，示例：8/3 普娃逆袭 已发布」。老板质问「我自然语言说的你不能给我转换成标准格式么」。前序迭代：2026-08-07《小席规划器与去约束化》（主控路由改大模型原生理解，规划器产出 params）。

## 目标

老板/发片同事用自然语言确认「已发布」、报发布数据，不需要背「日期 选题 数据」标准格式。成功标准：`《标题》已发布`（无日期、带书名号）→ 排期表按标题模糊匹配标「已发」；`昨天发的视频今日浏览3450、点赞87…`（无日期、无选题）→ 数据提取后按最近一条「已发」行回流；一条消息既说已发布又带数据 → 连动标已发+回流。

## 改动清单

- `controller.py`：
  - `_try_mark_published(content, params)`：优先用 planner params（date/topic）；正则兜底增强——剥 `《》「」『』` 及标点空白（`_normalize_topic`）后按标题**模糊匹配**待发行（`_fuzzy_topic_match` 双向包含比较），无日期也认；全不中回「没找到匹配的待发条目」。
  - `_reflow(msg, content, replies, params)`：优先用 params（date/topic/data）；无日期但带数据指标 → `_extract_metrics` 正则提取（浏览/播放/点赞/评论/收藏/转发/留资 + 数字，`万`→`w`）→ 按**最近一条「已发」行**回落存档（`_latest_published_row` 按 M/D 日期取最近）；仍无指标 → 维持「列出已发待回流」兜底。
  - `_exec_mark_published`：**连动**——标完「已发」后若同消息/参数带数据 → 直接对该行 `record_data` 回流。
  - `_ACTION_EXECUTORS`「数据回流」lambda 透传 params。
- `planner.py`：判断段补「报数据→数据回流，params 放 date/topic/data；没日期让系统按已发回落」；params 契约扩 `data`（数据回流的数据串），确认已发布/数据回流要把能认出的 date/topic/data 填进 params。
- `workspace/排期表.md`：8/7 19:17《新加坡私校集体收紧…》补标 `已发`/`待回流`（老板已在群里确认已发布，人工运维补标）。

## 架构影响

- **执行器从「只信标准格式」变「先信结构化 params、再兜底自然语言」**：planner 负责语义理解，执行器负责落地健壮性。params 是首选通道，正则兜底是防线，不再因为格式不标准就拒绝老板。
- 排期表「已发」仍**必须人工确认**（智能体不自动发片）——本轮只改「人类确认已发布的表述被系统听懂」，不改变确认来源。
- 数据回流对「无日期」的默认回落目标 = 最近一条「已发」行，语义上对应老板「刚发的那条」的日常表达。

## 第二轮（09:50）· 跨消息暂存待回流数据（解决上轮遗留①）

**背景**：老板报数据与确认已发布常分两条消息——报数据时该条还没标「已发」，系统只能「列出已发待回流」或「没找到」，数据丢了。本轮让「先报数据、后确认已发布」也能连动。

**改动清单**：
- `controller.py`：
  - 模块态 `_pending_reflow[chat_id]`（date/topic/data/ts）+ `_PENDING_REFLOW_TTL=7200s` + `_last_marked`（最近一次标「已发」成功的 (date,topic)）。
  - `_reflow`：无日期带指标但无「已发」行 → `_stash_pending` 暂存并回「数据已记下…等确认已发布自动回流」；行存在但未标已发 → 带标题暂存；均不再丢数据。
  - `_exec_mark_published`：标完「已发」后若同消息带数据 → 连动回流；否则检查 `_take_pending`（带日期/标题的暂存只在匹配刚标已发行的行时应用，防串台）→ 命中自动补回流。
- `scheduler.py` + `_try_mark_published`：**mark_published 匹配范围 待发→待产/待发**——真实排期行创建时全是「待产」（controller 4 处 add_entry），此前 mark_published 只认「待发」导致真实行永远标不了已发（潜在 bug，本轮顺手修复）。

**架构影响**：数据回流从「单消息原子」扩展为「跨消息可暂存」——数据先入暂存、后补账；TTL 防数据串台到隔太久的视频。已发仍必须人工确认不变。

**验证**：
- 新增 3 例：`test_reflow_pending_data_applies_on_later_publish`（先报数据无已发行→暂存→后确认已发布→自动回流）；`test_reflow_pending_topic_hint_waits_for_matching_publish`（带选题暂存，确认另一条不误配，确认正确那条才回流）；`test_reflow_pending_expires_not_applied`（超 TTL 只标已发不补回流）。
- 全量回归 controller 162 / scheduler 17 / intent 44 / experts 31 / planner 14 / rules 11 / context_store 10 / knowledge 9 / market 7 / session 6 / material 6 / pipe 5 / identity 5 / bots 5 / circuit 5 / used_topics 5 / reflow 3 / search 4 全绿。

## 第三轮（10:15）· params 路径精确匹配失败即放弃 → 解析器降级（生产复现 10:09）

**现象**：张艺宝确认孩子偏科已发布（含「8/7 19:45《孩子偏科…》」），小席回「未找到对应待发条目」。**根因**：planner 把「8/7 19:45」整个当 params.date，排期行 date 只有「8/7」，params 路径精确匹配失败就返回、不走模糊兜底（v1.6 缺陷）。

**改动**：新增 `_resolve_publish_row`（date 剥 M/D 去时间、topic 剥《》标点模糊匹配待产/待发行），params 路径与正则路径统一先经解析器再标；日期剥出且对不上时不强配，防误标错行。测试 +1（复现生产），controller 163 / scheduler 17 全绿，小席已重启。

**验证结论（回答老板「昨天在另一个群已确认发布」）**：老席留学ip数字专家群历史无「已发布」确认记录（最后一次 21:42 孙芳洁「好滴～」，18:45 提醒后只回「已准备好」≠已发布）；孩子偏科行按系统记录本就未确认发布。

## 遗留

- ~~**跨消息数据**：老板「记录刚刚的数据」若指上一条消息（无数字），仍无法连动~~ → 已解决（第二轮暂存）。仍剩边界：报数据消息里**完全无数字指标**（只说「记录刚刚的数据」）时，无从提取数据，暂存也救不了——需老板补数字。
- 确认已发布 params 日期剥出后若与行日期不符，即使标题唯一命中也不标（保守防误标）——若老板日期报错但标题明确，会回「未找到对应待发条目」，需后续权衡「唯一命中可忽略日期」。另：排期表无「已发布」人工确认记录时，老板坚称已发，只能人工问（本日案例即此类）。
- 「已发布」模糊匹配按双向包含（标题互相包含即中），极短标题可能误配；排期表标题重复时匹配到第一条待发行。长期可加「唯一性校验 + 多候选让老板挑」。
- 相对日期（昨天/今天）在确认已发布路径未换算（走标题匹配；数据回流路径按最近已发行回落），如需「昨天=8/7」显式换算需在 `_try_mark_published` 加日期解析。
