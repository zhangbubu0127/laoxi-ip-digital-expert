# 讨论记录 2026-08-10

本文件按「老板发现问题 → 讨论 → 整改 → 验证」逐条沉淀，与 `docs/变更记录/`（时间流水）、`docs/iteration/`（迭代记录）互为补充：这里记录"为什么改"。

---

## 1. 已核对好可以确定是已发了 → 小席回「没找到匹配的待发条目」

**老板反馈**：测试群 16:40 发「已核对好，可以确定是已发了」（刚定稿、刚上排期表）→ 小席回「已发状态：没找到匹配的待发条目，说清日期+标题」。老板质疑：刚讨论的选题、刚上传多维表格，应该知道是哪条。

**根因**：`_try_mark_published` 只在消息显式带「日期+标题」或标题模糊命中时才能定位行；消息无日期无标题 → 纯标题模糊匹配对不上 → 落「没找到」。执行器**没有回落「最近定稿选题」（`_last_passed`）**——8/8 排期意图兜底用的锚点，标已发这侧漏了。LLM 其实判对了 action=确认已发布，缺的是执行器用上下文定位行。

**整改**：`_try_mark_published` 无日期+标题也模糊不到时，用 `_last_passed[chat_id]` 最近定稿选题归一化后对 待产/待发 行模糊匹配；**唯一命中才标已发**，撞题歧义（多条可对上）不猜、明说让老板补日期/标题。

**验证**：test_controller 177→179（`_last_passed` 唯一命中→标已发；撞题歧义→不标让补日期标题）；真群过。

## 2. 早三年吧，然后就可以了 → 被「可以了」抢先当定稿

**老板反馈**：席小核疑问 v3「早六年上班」后老板回「早三年吧，然后就可以了」→ 系统只认「可以了」当放行定稿，直接进排期询问，「早三年」改稿指令被丢掉。

**根因**：`wait_boss` 下 `_resolve_doubt` 的 `_is_pass` 用**整条消息子串匹配** `_PASS_HINTS`（含「可以了」），消息同时含实质修改+放行词时放行词优先。该关键词门先于 planner LLM（handle_message 第 871 行 wait_boss 分流，planner 第 1333 行才轮到），LLM 根本没看到消息。关键词门是为防「放行话术被误当答案 → 改稿复审死循环」故意加的，盲区是没分辨「否定式放行」（不用改/别改）与「实质改稿指令」（早三年/8万/改成X）。

**整改**：`_resolve_doubt` 在 `_is_pass` 前加 `_has_concrete_modification`——消息含数字量词（\d+ 或 中文数+年/万/岁/个/条/月/天/小时/点）或肯定改稿动词（改成/换成/写成/改为/调成/删掉/去掉/加上/加个/挪到）→ 判实质修改走 落规则+席小文改稿，放行词不抢先；「不用改/别改/不用再改/不改了」否定式仍归放行。

**验证**：test_controller 179→181（走改稿路径不进排期询问 / 否定式仍放行）；真群过。
