## 1. 席小题选题依据追问「对不上」

**老板反馈**：对席小题所出选题依据追问，他答得不好；解释的原因不是他对应选题的原因，对不上。

**根因**（讨论后定位三条）：
1. 模型在一个输出内序号漂移——依据第 N 条 ≠ 上方第 N 条选题。
2. 存盘只存依据不存题目——追问时无法按题配对。
3. 无存依据时重新生成——生成一套对不上的依据。

**整改**：
- 席小题 prompt 强制【依据】段第 N 条=上方第 N 条选题，一一对应禁调换（`src/brain/experts/xiaoti.py`）。
- `context_store.save_basis/load_basis` 改存 `(topics, basis)` 配对（`src/brain/context_store.py`）。
- 追问按题配对回答「选题N「题目」依据：…」，无存依据时 fallback 给 explain 并带上次选题作上下文（`src/skin/multi_main.py` 的 `_match_basis_question/_paired_topics/_numbered_lines`）。

**验证**：全量 170 用例绿；群里实测「选题1「中考400分…」的依据：学制路径选题占31%…」配对正确。

## 5. 主控回复退回模板

**老板反馈**：我跟主控说「席小核都说要改了席小文怎么不改？」主控回答后，我赞同主控的回答让他继续做，但他的回复直接退回到模板了，这是怎么回事？

**根因**（日志 17:19 抓到）：deepseek 推理型模型偶发 `reasoning_tokens=200` 吃满 max_tokens=200、content 为空且 finish=length，`llm.py` 遇 length 直接抛错 → `_chat_reply` 降级模板「需要我做什么？…」。

**整改**：
- `src/brain/llm.py`：空内容（任意 finish）改为逐步加大 max_tokens 重试 3 次（×2 封顶 16000），仍空才抛；length 且有内容才判真截断。
- `_default_chat_generate` max_tokens 200→800→10000，system 加「直接给最终答复，不要输出思考过程」。

**验证**：controller 50 用例绿；重启后闲聊不再掉模板。

## 6. 推理吃满预算 / 对话预算多少

**老板提问**：推理吃满预算怎么回事，那拉高一点预算，别出现这种情况。市面上的其他项目调研一下对话预算用多少，可以适当高一点，到一万吧，可以看看github上怎么样。

**讨论结论**：`max_tokens` 是推理+正文总上限，推理型模型先出 `reasoning_content` 再出正文，预算太小被思考吃满 → content 空。调研 GitHub 实践：deepseek-chat 非思考模式上限 8K、deepseek-reasoner 思考模式默认 32K/上限 64K；社区项目常见 2K–8K（ComfyUI 1024、llm-quickstart 2000、DeepSeek-Reasonix 32768）。本项目 `deepseek-v4-flash` 为推理型，10000 在安全区间。

**整改**：`_default_chat_generate` max_tokens **800→10000**，配合 llm.py 空输出自动加预算重试。

**验证**：controller 50 用例绿；重启加载。

## 7. 小席连回两条

**老板反馈**：为啥小席连着回复我两条。

**根因**：17:39 重启时 kill 用的 pgrep 模式 `multi_main.py` 匹配不到实际命令行 `-m skin.multi_main`，旧进程（2269-2274）没被杀掉，两套小席同时消费同一群事件各回一条。日志实锤：17:37:09 与 17:37:15 收到同一条「这雨下的真大啊」分别回复两条。

**整改**：按 pid 杀掉旧进程，仅剩 2940-2945 一套，单进程消费。

**验证**：进程清单确认单套，日志确认单进程消费；变更记录 17:45 记载该坑（pgrep 模式要匹配 `skin.multi_main`）。
