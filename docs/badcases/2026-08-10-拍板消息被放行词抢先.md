# 拍板消息含实质改稿+放行词时，「可以了」抢先被当定稿

- **日期/群**：2026-08-10 17:02 · 测试群 oc_eed170…
- **状态**：已修复
- **触发输入**：早三年吧，然后就可以了
- **实际行为**：席小核疑问 v3「早六年上班」后老板回这句 → 系统只认「可以了」当放行定稿，直接进排期询问，「早三年」改稿指令被丢掉。
- **期望行为**：「早三年」是实质改稿答案，应走 落规则+席小文改稿 路径，而不是当纯放行。
- **根因**：`wait_boss` 下 `_resolve_doubt` 的 `_is_pass` 用**整条消息子串匹配** `_PASS_HINTS`（含「可以了」），消息同时含实质修改+放行词时放行词优先。该关键词门先于 planner LLM（handle_message 第 871 行 wait_boss 分流 → `_resolve_doubt`，planner 第 1333 行才轮到），LLM 根本没看到这条消息。关键词门本身是为防「放行话术被误当答案 → 改稿复审死循环」故意加的，盲区是没分辨「否定式放行」（不用改/别改）与「实质改稿指令」（早三年/8万/改成X）。
- **修复**：`controller.py` `_resolve_doubt` 在 `_is_pass` 前加 `_has_concrete_modification` 判定——消息含数字量词（\d+ 或 中文数+年/万/岁/个/条/月/天/小时/点）或肯定改稿动词（改成/换成/写成/改为/调成/删掉/去掉/加上/加个/挪到）→ 判实质修改走 落规则+席小文改稿，放行词不抢先；「不用改/别改/不用再改/不改了」否定式仍归放行。
