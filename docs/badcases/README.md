# Bad Case 收集库

**定位**：记录真实环境（测试群/生产群）里小席犯过的错——原话输入、错误输出、根因、修复、回归测试。是调试的参考书，也是防回归的清单。

**为什么单独放**：`docs/iteration/` 记「改了什么」，bad case 记「错在哪、为什么错」。改代码/加新能力前扫一遍索引，同类坑不踩第二次。2026-08-10 起立库，回填 08-08/08-09 已复盘的案例。

## 目录结构

```
docs/badcases/
  README.md                      本文件：约定 + 索引
  YYYY-MM-DD-<短横线slug>.md     每篇一个 bad case
```

## 什么算 bad case

真实群里的**错误行为**，满足任一条即可收录：

1. 回复错误/答非所问（该做 A 做了 B）
2. 高后果误操作（误标已发、垃圾占位行、误改排期）
3. 找不到本该找到的（明明有上下文却说没有）
4. 该 LLM 能判断却扔模板话/放弃（「没找到」「未识别」类）
5. 容错缺失（用户笔误/口语就崩，正确做法是容忍+注明）

纯聊天风格不合、非行为错误的，不进库。

## 条目字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 标题 | ✅ | 一句话说清错在哪 |
| 日期/群 | ✅ | YYYY-MM-DD HH:MM + 群标识（测试群 / 生产群 oc_xx） |
| 状态 | ✅ | 已修复 / 待验证（生产重测）/ 待修复 |
| 触发输入 | ✅ | 真实原话（去掉 @bot 前缀） |
| 实际行为 | ✅ | 系统错误回复/行为 + 日志证据 |
| 期望行为 | | 应该怎样 |
| 根因 | ✅ | 一句话根因：为什么错（代码/架构层面） |
| 修复 | ✅ | 改动文件 + 要点 |
| 回归测试 | ✅ | 新增测试名 + 当时用例数 |
| 关联 | | 迭代记录 / 架构书版本 / 变更记录 |

## 维护约定

- 每次修复后**当天**补录；测试/生产遇新 bad case 当场记，别等。
- 修完先标「待验证」→ 真群过一遍确认再改「已修复」。
- 已修复案例**不删**，状态标记，防止复发——改代码前扫一遍索引。
- 每加一篇，同步更新本 README 索引行（新案例置顶）。
